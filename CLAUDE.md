# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Язык

В этом репозитории всё пишется на русском: ответы, документация, комментарии в коде, сообщения в логах, сообщения коммитов и описания PR. Идентификаторы, команды, имена файлов и переменных окружения не переводятся.

Заголовок коммита: `<префикс>: <что сделано>`, префикс тоже на русском:

- `исправление` — исправление ошибки в поведении бота;
- `возможность` — новая возможность для пользователей;
- `документация` — только документация и `TODO.md`;
- `зависимости` — обновление зависимостей (этот же префикс ставит Dependabot);
- `инфраструктура` — CI, Docker, сборка и окружение;
- `рефакторинг` — изменение кода без изменения поведения;
- `тесты` — только тесты.

## План работ

План доработок лежит в `TODO.md`. Читай его в начале каждого диалога. Когда изменение готово, отметь пункт `[x]` и добавь `TODO.md` в стейдж вместе с кодом: пункт закрывается тем же коммитом, что и изменение, без хеша. Коммитит только пользователь: сам `git commit`, merge и push не выполняй, даже если он пишет «можно коммитить». Если он решил изменение не коммитить, отметку убери.

## Обзор

Telegram-бот на Go (`github.com/mymmrac/telego` v1.12, нужен Go 1.26.7 или новее — этого требует telego). Принимает объявления, присланные ему в личный чат, и публикует их в заданный канал с припиской «by: <автор>». После публикации бот отвечает автору сообщением с inline-кнопкой, которая помечает объявление как неактуальное («Не актуально») или восстанавливает его. Все тексты для пользователей на русском.

## Команды

```sh
go build ./...            # сборка (модуль `github.com/golman/telegram-bot`: `main` в корне и `internal/post`)
go run .                  # локальный запуск (нужны переменные окружения ниже)
go vet ./...
go test -race ./...       # все тесты всех пакетов
go test -run TestName ./internal/post/   # один тест (путь — пакет теста, `.` — корень)
docker compose up -d --build   # запуск в Docker, переменные из .env
```

Образ (`Dockerfile`): сборка на `golang` последней стабильной версии, запуск на `distroless/static` без shell от пользователя nonroot (65532). Оба образа закреплены по digest и обновляются Dependabot. Логи пишутся в том `logs` (`/app/logs`) и в stdout (`docker compose logs`). `stop_grace_period: 30s` в `docker-compose.yml` даёт боту дождаться конца long polling и отправить накопленные альбомы.

CI (`.github/workflows/ci.yml`) на каждый push в `master` и PR запускает `gofmt`, `go mod tidy -diff`, `go vet`, `go test -race`, staticcheck, govulncheck и сборку на двух версиях Go: минимальной из `go.mod` и последней стабильной (`stable`). Actions закреплены по SHA; их и Go-модули обновляет Dependabot (`.github/dependabot.yml`, раз в неделю, одной PR на экосистему). Версии staticcheck и govulncheck закреплены в `go run …@vX` прямо в workflow, Dependabot их не видит — обновляй вручную.

## Конфигурация (переменные окружения)

Читаются через типизированные хелперы в `logging.go` (`getEnvOrDefault`, `getEnvIntOrDefault`, `getEnvInt64OrDefault`, `getEnvBoolOrDefault`). Используй их вместо прямого `os.Getenv`: некорректные значения логируются, и подставляется значение по умолчанию.

- `BOT_TOKEN` (обязательно), `CHANNEL_ID` (обязательно, int64 — целевой канал)
- `BOT_AUTH_ENABLED` (по умолчанию `true`) — принимать объявления только от участников канала `CHANNEL_ID`
- `LOG_FILE_PATH` (по умолчанию `logs/telegram-bot.log`), `LOG_MAX_SIZE_MB`, `LOG_MAX_BACKUPS`, `LOG_MAX_AGE_DAYS`, `LOG_COMPRESS` — ротация через lumberjack; логи пишутся и в stdout, и в файл
- `LOG_LEVEL` (по умолчанию `info`) — `info` или `debug`, уровень и логов бота, и логов telego. Логи telego идут в тот же лог через `telegoLogger` (`logging.go`) с маскировкой токена; на `info` пишутся только его ошибки, на `debug` — ещё запросы и ответы API с текстами объявлений и данными пользователей, поэтому `debug` только для отладки

## Архитектура

Бот лежит в плоском `package main` в корне; сборка вида поста вынесена в пакет `internal/post`, он от бота не зависит. Структура `VBBot` (`telegram-bot.go`) хранит клиент бота, ID канала, конфиг и собираемые медиагруппы.

- **Один цикл событий.** `VBBot.Start` делает `select` по каналу обновлений long polling и секундному тикеру (`albumTickInterval`). Вся обработка идёт в этой одной горутине, поэтому `mediamsg` — обычная map без блокировок. Сохраняй это, а если добавляешь горутины, добавь и синхронизацию. Каждый update обрабатывается в `dispatch` под `recover`; шаг тикера — метод `tick()`, а каждый альбом отправляется в `publishAlbum` тоже под `recover` (из `tick()` и при остановке). **Остановка.** `main` отменяет `ctx` по SIGINT/SIGTERM (`signal.NotifyContext`; повторный сигнал завершает процесс сразу). telego прекращает long polling и закрывает канал, а `Start(ctx, ch)` дочитывает буфер канала (Telegram уже считает эти обновления доставленными), публикует накопленные альбомы (`flushMediaGroups`) и возвращает `nil`. Если канал закрылся без отмены `ctx`, `Start` возвращает `errUpdatesClosed`, и процесс завершается с кодом 1.
- **Обработка сообщения.** `/команды` отсекает `dispatch`, затем `handleUpdate` игнорирует всё, кроме личного чата (`Chat.Type != ChatTypePrivate`), и сообщения без `From`. Элемент альбома уходит в `addAlbumItem` (см. «Медиагруппы»). Остальные сообщения проходят `admit`: `authByChannel` (`auth.go`; возвращает `(bool, error)`, при ошибке пользователь получает `AuthCheckFailedMessage`) и `runFilter` (`filter.go`; возвращает `true`, если сообщение нужно *отклонить*, пока фильтров нет). Затем сообщение, которое не текст и не фото (стикер, видео, документ, геолокация…), отклоняется одним `UnsupportedMessage`, иначе уходит в `sendPlainMessage` / `sendPhotoMessage` (`send.go`). Текст или подпись обязательны, пустые сообщения отклоняются.
- **Сборка поста.** Текст и entities поста для публикации, пометки «Не актуально» и восстановления собирает одна функция `post.Build` (пакет `internal/post`) из `post.Source` (текст, entities, ID и имя автора, признак медиа): тело получает только разметку автора (бот своего форматирования не добавляет), приписка `post.AuthorSuffix`, при `deprecated` — префикс `post.DeprecatedPrefix` (обе константы — часть вида поста и лежат в `internal/post`, а не в `phrases.go`), зачёркивание и сдвиг пользовательских entities на UTF-16-длину префикса. Перед отправкой `rejectTooLong` (`send.go`) сверяет длину текста с `post.TextLimit`: лимит Telegram (`post.MaxTextLen` 4096 для текста, `post.MaxCaptionLen` 1024 для подписи, в UTF-16) минус всё, что добавляет бот, считая по виду поста «Не актуально». Слишком длинное объявление не публикуется, автор получает ответом на своё сообщение `postTooLongText` (`phrases.go`, пакет `main`) — на сколько символов сократить текст. Пост из сообщения автора собирает `post.FromMessage`, имя для приписки — `post.DisplayName`.
- **Медиагруппы.** Фото из альбома Telegram присылает отдельными обновлениями с общим `MediaGroupID`. Они собираются в `MediaMessage` (`mediamessage.go`, `newMediaMessage` / `addItem`; подпись, её entities и ID сообщения для ответа берутся с элемента, где есть подпись, при нескольких — с последнего), а тикер отправляет его, когда после последнего фото прошло `albumQuietPeriod` (3 секунды) тишины: состояния `Init → (отправка) → ToDelete → удаление`. Каждое новое фото откладывает отправку, поэтому медленно загружаемый альбом не разрывается. Время берётся из `clock()`, в тестах его подменяет `useFakeClock`. В `ToDelete` отправленный альбом хранится ещё `albumLateWindow` (минуту): фото, пришедшие в это время, не публикуются, а автор один раз получает `AlbumItemLateMessage` (`rejectLateAlbumItem`). Фото, опоздавшие сильнее, по-прежнему создают новый альбом без подписи. Подписка и фильтры (`admit`) проверяются один раз на альбом, на первом пришедшем элементе: при отказе автор получает одно сообщение, а накопитель с `rejected` молча отбрасывает остальные элементы до конца окна. `MediaGroupDelayMessage` уходит, только когда у альбома есть и фото, и подпись (`promised`). Видео и файлы в альбоме не публикуются, но их подпись берётся (`skipped` считает пропущенные): после публикации автор один раз получает `AlbumSkippedMessage`, а альбом без единого фото отклоняется `UnsupportedMessage`. Альбом публикуется одним `SendMediaGroup` примерно через 3–4 секунды после последнего фото. Подпись ставится только на первый элемент.
- **Callback-кнопки** (`callback.go`). Формат callback data: `"<действие>_<chatID канала>_<messageID в канале>"`, где действие — `delete` или `restore`; кодируется `encodeCallback` / `decodeCallback`, формат менять нельзя — в чатах лежат старые кнопки. Один обработчик `handleCallbackQuery` сверяет chatID с каналом, пересобирает пост из `ReplyToMessage` (исходного сообщения автора, на которое ответило подтверждение) через `post.FromMessage` и `post.Build`, редактирует текст или подпись поста и переключает кнопку (`toggleKeyboard`). `AnswerCallbackQuery` вызывается ровно один раз, в `defer`. Ответ Telegram «message is not modified» (`isNotModified`) — успех: пост или подтверждение уже в нужном состоянии, например после повторного нажатия.
- **Ошибки API.** Пользователь получает только понятный текст: `reportPublishError` (`send.go`) при неудачной публикации, `ConfirmFailedMessage`, если пост опубликован, а подтверждение не ушло. Подробности ошибки пишутся в лог. Если не ушло служебное сообщение пользователю, ошибка только логируется. Все запросы идут через `rateLimitCaller` (`ratelimit.go`): он повторяет только ответ 429 после `retry_after` (до 3 попыток, ожидание не дольше 30 секунд, оно блокирует цикл событий). Сетевые и прочие ошибки не повторяются, иначе после потерянного ответа объявление опубликовалось бы дважды. Под ним `timeoutCaller` даёт каждой попытке дедлайн `apiTimeout` (15 секунд, больше long polling `longPollTimeoutSeconds`); цепочку собирает `newAPICaller`. В коде запросы по-прежнему идут с `context.Background()`: контекст остановки туда не передаётся, иначе после сигнала не удалось бы дообработать буфер и отправить альбомы.
- **Логи** (`logging.go`): `log/slog`, текстовый формат `key=value`, время в UTC (`newLogHandler`). Сообщение — короткая фраза на русском без подстановок (исключение — записи telego: их текст приходит из библиотеки уже готовым), подробности — в полях с едиными именами: `user_id`, `chat_id`, `message_id`, `update_id`, `media_group_id`, `channel_msg_id`, `err`. Уровни: `Error` — потеря данных или паника, `Warn` — сбой внешнего вызова или некорректная настройка, `Info` — заметные события, `Debug` — подробности. Пакет `log` не используй.
- Все тексты для пользователей — константы в `phrases.go`, по группам (приём объявления, альбомы, публикация, кнопки), кроме вида поста (`post.DeprecatedPrefix`, `post.AuthorSuffix`) — он в `internal/post`. В обработчиках строк для пользователей нет, в тестах тексты сверяются через эти константы.
- **Тесты.** `fakeapi_test.go` — фейковый Bot API на `httptest` (`newTestBot`; `fail` — ошибка метода, `respond` — свой JSON-ответ), с ним тестируются обработчики без сети; там же разбор запросов (`jsonString`, `authorTexts`, `channelCalls` и др.). Общие данные и конструкторы сообщений — в `testhelpers_test.go`: `testAuthorID`, `testConfirmMessageID`, `authorMessage`, `albumItem`, `confirmMsg`, `pendingAlbum`, а также `captureLog` и `useFakeClock`. Новые хелперы клади туда же, а не в файл теста. Сообщения об ошибках в тестах — на русском, в виде «получено X, ожидалось Y». Сквозной тест альбома — `album_test.go`.

## Подводные камни

- Остановка по сигналу занимает до 8 секунд: fasthttp в telego прерывает запрос только по дедлайну, а не по отмене `ctx`, поэтому текущий `getUpdates` дожидается конца long polling. Столько же длится пауза перед повтором после ошибки `getUpdates`.
- `Message.From` проверяется на nil в начале `handleUpdate`; `authByChannel` и `send.go` полагаются на это и разыменовывают его без проверки. Если вызываешь их откуда-то ещё, проверь `From` сам.
